### 1.3 Elasticsearch 授权边界

Elastic 官方资料显示：dense vector 存储与检索存在基础授权可用路径，但内置 RRF 等完整 ESRE 能力属于更高订阅层级。P0 的设计结论保持为：

```text
Elasticsearch：BM25、过滤、dense_vector/kNN、排序结果
Java 应用层：并行请求、RRF、Parent 聚合、Rerank 编排
```

这不是因为 ES 不能执行 RRF，而是为了授权可移植性、版本隔离和 Query Trace 可解释性。未来购买相应订阅后，可以把 ES 内置 RRF 作为额外 Profile 对照，但不能替换应用层基线。

### 1.4 Elasticsearch 8.18 向量注意事项

Elasticsearch 8.18 支持 `dense_vector`、HNSW 近似 kNN 与 `script_score` 精确检索。TV-01 使用 exact/brute-force 小样本作为 Recall 校准真值，并分别记录向量索引类型、维度、相似度、量化配置和资源消耗，不能只测延迟。

## 2. 所有技术验证的统一规则

### 2.1 固定输入

```text
功能语料：16 SourceDocument / 17 DocumentVersion
检索评测：20 Smoke Cases（全部 DEV）
解析标注：每种结构至少 3 个手工锚点
OKF 标注：选取 8 份文档建立人工 Concept/Relation Gold
容量语料：从虚构语料生成只用于性能的 10k / 100k Chunk 数据
```

容量语料不能进入质量评测，只用于索引时间、内存和延迟测试。

### 2.2 单变量原则

- 一轮只改变一个主要变量；
- 所有候选使用同一 CorpusVersion 和 DatasetVersion；
- 模型、Prompt、Chunk 和索引参数必须有版本号；
- 调参只使用 DEV；
- 未来建立 TEST 后，不能根据 TEST 结果反向调参；
- 每项性能实验先预热，再执行至少 5 轮并记录分布。

### 2.3 环境固定

每次运行记录：

- OS、CPU、内存、磁盘；
- GPU 型号、显存和驱动（使用 GPU 时）；
- JDK、Maven 和容器运行时版本；
- Elasticsearch 节点数、Heap、插件和 License；
- Parser/Model 服务镜像 Digest；
- 并发数、批大小和超时；
- 冷启动或热启动；
- Git Commit 和未提交修改摘要。

### 2.4 决策方式

候选选择使用“硬门禁 + Pareto 比较”：

1. 先淘汰权限、版本、引用、来源等硬门禁失败项；
2. 再比较质量、延迟、资源、成本和维护风险；
3. 不把多个指标强行合成一个不透明总分；
4. 质量相近时选择依赖更少、授权更清晰、运维更简单的方案；
5. 未获胜候选保留结果，不删除失败证据。

## 3. TV-01：Elasticsearch、客户端与中文检索

### 3.1 实验问题

- 8.18.8 官方 Java Client 与 8.18.x 同 minor 服务端是否完整兼容；
- Boot 原生客户端是否覆盖 P0 所需索引、Alias、Bulk、BM25、过滤和 kNN API；
- 官方分析器与 IK 对中文金融词汇的效果差异；
- 默认量化 HNSW 对 Recall 的影响；
- 扁平 Child + `parentId` 是否满足 Parent/Child 聚合；
- Alias 发布、回退和过滤能否稳定工作。

### 3.2 候选矩阵

| 维度 | A | B | 备注 |
|---|---|---|---|
| Server | ES 8.18.x，优先 8.18.8 | 更高 8.x minor 仅做前向兼容观察 | P0 主线不跨到 9.x |
| Java Client | Boot BOM 管理的 8.18.8 | 不设置第二套客户端 | 不测试 RHLC/Easy-ES |
| 中文 Analyzer | `cjk`/standard + ICU 规范化 + 同义词 | IK + 金融自定义词典 | IK 为第三方插件，必须验证精确版本和运维 |
| Vector | 默认量化 HNSW | exact `script_score` 小样本 | exact 只做 Recall 校准，不作为规模方案 |
| Parent 关联 | 扁平 Child + `parentId` | nested/join 对照 | 默认倾向 A |
| Fusion | 应用层 RRF | ES 内置 RRF（仅授权允许时观察） | 应用层必须始终保留 |

Analyzer 金融词表至少包含：

```text
启航经营贷
税信快贷
安业抵押贷
实际控制人
抵押率
税务数据授权书
授信审批
贷前调查
```

### 3.3 实验阶段

```text
TV-01A  客户端/API功能覆盖
TV-01B  Analyzer Token与BM25效果
TV-01C  dense_vector Recall与延迟
TV-01D  10k/100k容量与资源
TV-01E  Alias切换、回退和故障恢复
```

### 3.4 指标

- API 覆盖和实现复杂度；
- Analyzer Token 结果和领域词完整率；
- BM25 Recall@20、MRR@10、nDCG@10；
- Vector Recall@20 相对 exact 真值的损失；
- 查询 P50/P95；
- Bulk 吞吐、失败率和重试；
- 10k/100k Chunk 的索引大小、Heap 和构建时间；
- KnowledgeBase、PublicationRevision、权限过滤正确率；
- Alias 切换期间错误率；
- 插件安装、升级和离线部署成本。

### 3.5 硬门禁

- 过滤正确率必须为 100%；
- Alias 切换后不能同时暴露两个活动版本；
- 旧 Alias 回退可验证；
- Java Client 不存在 P0 API 阻塞；
- 插件版本与 Server 不精确兼容时淘汰该插件候选；
- 应用层 RRF 结果可复现。

### 3.6 推荐停止条件

- ES 8.18.x 同 minor 服务端 + 8.18.8 官方客户端通过全部门禁后，不继续穷举其他版本；
- IK 如果无法提供目标 ES 精确版本、稳定离线安装或升级路径，直接采用官方 Analyzer 组合；
- 100k Chunk 已能观察趋势，P0 不扩展到百万级压力测试；
- 量化 Recall 损失超过候选容忍值时，保留 exact 校准并调整索引类型/参数，不通过增加 TopK 掩盖问题。

## 4. TV-02：Parser Profile 与 SourceAnchor

### 4.1 候选矩阵

| Profile | 实现候选 | 适用输入 | 定位 |
|---|---|---|---|
| TIKA_TEXT | Apache Tika 3.3.2 | DOCX、Markdown、TXT、简单文本 PDF | 稳定文本基线 |
| MINERU_LAYOUT | MinerU 3.1.10 独立服务 | 表格和复杂版式 PDF | 布局增强候选 |
| AUTO_ROUTED | 文件特征路由到前两者 | 混合语料 | 最终产品 Profile 候选 |
| OCR_OBSERVE | MinerU/OCR 可用路径 | 额外扫描 PDF | 只评估，不纳入 P0 承诺 |

Tika 4.0.0-beta-1 不进入 P0 候选，因为官方标记为预览且 API 仍可能变化。

### 4.2 输入分层

```text
P1  原生文本 PDF
P2  多列表格 PDF
P3  跨页表格 PDF
P4  DOCX Heading/List/Table
P5  Markdown Frontmatter/Link
P6  TXT 编号段落
P7  扫描 PDF（观察项）
```

### 4.3 标注

每份文件人工标注：

- 标题层级；
- 关键段落文本；
- 列表项；
- 表格行、列和单元格；
- 黄金语义 SourceAnchor；
- 页面与区域；
- 阅读顺序。

### 4.4 指标与门禁

| 指标 | 目标性质 |
|---|---|
| Parse Success | 支持格式硬门禁 |
| Text Coverage | 关键事实不能丢失 |
| Heading/List F1 | 结构质量 |
| Table Cell F1 | 表格质量 |
| Reading Order Accuracy | 多栏/复杂布局 |
| SourceAnchor Accuracy | 引用硬门禁 |
| P50/P95、峰值内存 | 运行指标 |

硬门禁：Smoke Case 的 Primary Evidence 不能因解析丢失；Anchor 不得定位到错误页或错误条款；解析失败必须显式返回，不能静默换 Parser 后当作成功。

### 4.5 路由决策模板

```text
DOCX / Markdown / TXT         → TIKA_TEXT
简单原生文本 PDF              → 先比较后决定
复杂表格/版式 PDF             → MINERU_LAYOUT
扫描 PDF                      → P0 显示不支持或观察性解析
```

## 5. TV-03：Chunk、Embedding 与 Reranker

### 5.1 分阶段矩阵

禁止直接跑所有组合的笛卡尔积。采用三阶段淘汰。

| Chunk Profile | Child | Parent | Overlap | 特点 |
|---|---:|---:|---:|---|

| 候选 | 维度/特点 | 验证重点 |

| Qwen3-Embedding-0.6B | 最大 1024 维，支持 MRL 和指令 | 1024 vs 512 维、中文金融指令 |
| BGE-M3 | 多语言、最长 8192、支持多种检索形式 | 先只使用 dense 输出，避免同时改变检索方式 |
| External API Baseline | 供应商待定 | 仅在用户已有可用服务时加入 |

先固定 TV-01 Analyzer 胜出项，执行 `3 Chunk × 2 Embedding = 6` 组。

```text

bge-reranker-v2-m3
```

#### 阶段 C：参数微调

只对最终两个候选调整：

```text
BM25 TopK       20 / 30 / 50
Vector TopK     20 / 30 / 50
RRF Window      20 / 30
Rerank TopN     6 / 8 / 10
```

### 5.2 输入文本约定

```text
rawText        仅用于展示和引用
embeddingText  headingPath + 类型提示 + 原文
displayText    面向回答的完整 Parent 文本
```

Embedding 指令、归一化、最大长度和截断策略必须版本化。

### 5.3 指标

- Recall@20、MRR@10、nDCG@10；
- 表格问题、规则问题、版本问题分组指标；
- Parent Evidence Coverage；
- Embedding 吞吐、P95 和存储；
- Rerank P95、GPU/CPU 资源和增益；
- 512/1024 维质量损失与索引空间差异；
- 降级到 BM25 时的可接受性。

### 5.4 选择规则

- Recall@20 未达到候选门禁的 Embedding 直接淘汰；
- Reranker 必须证明 nDCG/MRR 有稳定提升，不能只看个别问题；
- 增益很小但延迟明显增加时，Reranker 不作为默认 Profile；
- 模型胜出不意味着把模型 SDK 暴露给业务层；
- P0 至少保留一个本地候选和一个可替换接口。

## 6. TV-04：Publication Saga、幂等与回退

### 6.1 固定场景

| ID | 场景 | 预期不变量 |
|---|---|---|
| PUB-01 | 首次发布 | 一个活动 PublicationRevision |
| PUB-02 | 相同幂等键重复请求 | 不产生重复 Chunk/Revision |
| PUB-03 | Embedding 中途失败 | 旧版本继续服务，任务可重试 |
| PUB-04 | ES Bulk 部分失败 | 暂存数据不可见，保存失败明细 |
| PUB-05 | 校验后、激活前失败 | Alias 不切换 |
| PUB-06 | 激活后 Outbox 确认失败 | 重试不能二次激活 |
| PUB-07 | 两个版本并发发布 | 最多一个成为活动版本 |
| PUB-08 | 发布新版后回退指定旧版 | Query 使用指定历史版本 |
| PUB-09 | 仅撤回、不回退 | 正式检索不返回该文档 |
| PUB-10 | 发布期间进程重启 | 从持久状态继续或安全失败 |
| PUB-11 | 永久删除来源 | 历史引用按删除规则处理 |
| PUB-12 | ES 对账发现孤儿数据 | 可识别并安全清理/重建 |

### 6.2 记录内容

- MySQL 状态前后；
- Outbox 事件；
- MinIO Manifest；
- ES 暂存与活动 Alias；
- 幂等键；
- 重试次数；
- Query 可见结果；
- 恢复操作和耗时。

### 6.3 立即失败条件

出现以下任一情况，候选发布方案直接失败：

- 同时存在两个活动 PublicationRevision；
- 新版失败导致旧版不可检索；
- 重试产生重复业务版本或重复检索数据；
- MySQL 指向的活动版本与 ES 可见版本无法对账；
- 未完成校验的数据被正式 Query 读取。

## 7. TV-05：OKF 提取、合并与来源绑定

### 7.1 Gold 子集

选择 8 份文档：

```text

FIN-005、FIN-010、FIN-013、FIN-015
```

人工标注建议规模：

```text
30～40 个 Concept

6～10 组重复/不应合并对
```

必须包含：同名不同版本、摘要与权威文档重复、规则与材料关系、流程先后关系。

### 7.2 提取矩阵

| 维度 | 候选 A | 候选 B |
|---|---|---|
| Prompt | 通用 Schema Prompt | 按 Concept Type 的模板 Prompt |
| 提取 | 单次结构化提取 | 类型识别后再抽属性/关系 |
| 合并召回 | 标题规范化 + Embedding | 标题/类型/属性/来源/生效区间联合 |
| 合并决策 | 全部人工 | LLM 只给建议 + 全部人工 |
| 渲染 | LLM Markdown | Java 确定性渲染 |

`LLM Markdown` 只作为失败对照，不允许进入最终架构。正式候选必须是结构化输出 + Java 渲染。

模型层先用两个可用的质量档：

```text
LLM-A  低成本结构化输出模型
LLM-B  高质量结构化输出模型
```

在用户确认模型供应商和部署条件后再替换为具体型号，避免实验设计反向绑定厂商。

### 7.3 指标

- Concept Precision/Recall/F1，按类型分组；
- Type Accuracy；
- 属性准确率；
- Relation Precision/Recall/F1；
- Source Binding Validity；
- Merge Pair Precision/Recall；
- 错误合并率；
- 人工确认、修改、排除率；
- 单文档 Token、延迟和成本；
- OKF Conformance Rate。

### 7.4 硬门禁

- 发布 Concept 来源绑定有效率 100%；
- V1/V2 年龄规则不能错误合并；
- LLM 输出不能直接成为最终 Bundle 文件；
- 高相似度合并建议必须人工裁决；
- 无有效 Primary Evidence 的 Candidate 不能确认。

## 8. TV-06：回答、引用、拒答与Evaluation Run

### 8.1 分阶段矩阵

#### 阶段 A：检索固定，比较回答协议

| 协议 | 说明 |
|---|---|
| A1_TEXT_CITATION | 模型生成带 Citation ID 的文本，生成后校验 |
| A2_CLAIM_FIRST | 先生成结构化 Claim + Evidence IDs，再由 Java 渲染答案 |

推荐重点验证 A2，因为它更容易进行确定性引用校验，但需要评估回答自然度和实现复杂度。

#### 阶段 B：证据充分性与拒答

| Gate | 说明 |
|---|---|
| G1_RULE | 无结果、版本/权限失败、低于最低检索阈值时规则拒答 |
| G2_MODEL | LLM 判断证据是否支持回答 |
| G3_COMBINED | 硬规则先行，模型只处理语义充分性 |

推荐 G3；LLM 不得覆盖权限、版本和引用合法性。

#### 阶段 C：OKF 增益

```text
Chunk-only Retrieval
vs
Concept Retrieval → Source Binding → Chunk Retrieval
```

只比较多跳、对比和术语问题；精确事实问题不强制经过 OKF。

### 8.3 指标与硬门禁

- Faithfulness；
- Factual Correctness；
- Required Claim Coverage；
- Forbidden Claim Rate；
- Citation Precision/Recall；
- Citation ID Validity；

## 12. 当前推荐结论

以下仍需实验确认，但可以作为首轮候选顺序：

1. 优先验证 Elasticsearch 8.18.x 同 minor 服务端 + Boot 管理的官方 Java Client 8.18.8；
2. 更高 8.x minor 只做前向兼容观察，Elasticsearch 9.x 延后到 P1 或框架再次升级时评估；
3. 坚持应用层 RRF，不把商业授权能力作为 P0 必需依赖；
4. 中文 Analyzer 比较官方 ICU/CJK 组合与 IK，不预先假定 IK 一定更好；
5. Tika 3.3.2 作为稳定文本基线，MinerU 3.1.10 作为独立布局解析候选；
6. Embedding 比较 Qwen3-Embedding-0.6B 与 BGE-M3；
7. Reranker 比较 NONE、Qwen3-Reranker-0.6B、bge-reranker-v2-m3；
8. 回答优先验证 Claim-first + Java 渲染与校验；
9. OKF 继续坚持结构化候选 + Java 渲染 + 人工合并。

## 13. 本阶段确认门

执行任何技术实验前，需要确认：

1. 是否接受 ES 8.18.x 同 minor 服务端为 P0 主候选，优先精确对齐 8.18.8；
2. 是否接受 P0 坚持应用层 RRF；
3. 是否接受 Tika 3.3.2 与 MinerU 3.1.10 的 Parser 矩阵；
4. 是否接受 Qwen3/BGE 两组 Embedding 与 Reranker 候选；
5. 是否接受先 20 个 Smoke、后 120 个完整用例；
6. 是否接受所有实验先写 Charter、再执行、最后形成 ADR；
