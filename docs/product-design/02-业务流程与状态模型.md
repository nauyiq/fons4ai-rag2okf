# 业务流程与状态模型

## 1. 核心对象关系

```text
KnowledgeBase
├── SourceDocument
│   └── DocumentVersion
│       └── ParseRevision
│           ├── ParsedBlock
│           ├── SourceAnchor
│           └── PublicationRevision
├── KnowledgeBundle
│   ├── OKFBuild
│   ├── KnowledgeConcept
│   │   └── ConceptRevision
│   └── BundleRevision
└── QueryTrace / AnswerEvidence
```

关键原则：

- 原始文档是证据；
- Parsed Block 是结构化解析结果；
- OKF Concept 是知识库级派生知识；
- Chunk 与向量是可重建的检索投影；
- Elasticsearch 不能成为唯一事实来源。

## 2. 文件、解析和发布独立状态

### 文件状态

```text
AVAILABLE
ARCHIVED
DELETED
```

### 解析状态

```text
NOT_STARTED
QUEUED
PARSING
SUCCEEDED
FAILED
```

### RAG 发布状态

```text
UNPUBLISHED
PUBLISHING
PUBLISHED
PUBLISH_FAILED
WITHDRAWN
```

三个维度不能合并成单一的“文档状态”。

## 3. 上传策略组合

| autoParse | autoPublish | 上传后的行为 |
|---|---|---|
| false | false | 只保存原文件，用户后续手动解析和发布 |
| false | true | 手动解析成功后自动进入发布流程 |
| true | false | 自动解析，成功后等待人工发布 |
| true | true | 自动解析，成功后自动发布 |

单次上传允许覆盖知识库默认值。

不解析的文件：

- 保留查看和下载能力；
- 不生成 Parsed Block；
- 不生成 Chunk；
- 不进入 RAG；
- 不参与 OKF 构建。

## 4. 文档解析流程

```text
原文件
→ 选择 Parser Profile
→ 解析页面、标题、段落、列表、表格和图片
→ 生成 Parsed Document
→ 生成 Source Anchor
→ 保存解析预览
```

解析阶段操作 MySQL 和 MinIO，不执行 Embedding，不写 Elasticsearch。

MVP 中 Parsed Block 只读。解析错误通过更换 Parser Profile 或重新解析处理。

## 5. RAG 发布流程

```text
ParseRevision
→ Parent/Child 切分
→ 内容增强
→ Embedding
→ Elasticsearch 暂存写入
→ 数量与字段校验
→ 激活 PublicationRevision
```

发布是可重试、幂等的 Saga/Outbox 流程，不是简单修改 `PUBLISHED` 状态。

自动发布和人工发布必须复用同一流水线。新版本失败时继续使用旧的活动版本。

## 6. OKF 构建流程

OKF 与文档 RAG 发布解耦：

```text
选择多个成功的 ParseRevision
→ 逐文档提取 Concept Candidate
→ 跨文档归一化和去重
→ 关系建议
→ 人工确认/合并/排除
→ OKF 校验
→ 生成 BundleRevision
→ Concept Embedding
→ 写入 Concept 索引
→ 激活 BundleRevision
```

OKFBuild 状态：

```text
CREATED
→ EXTRACTING
→ CONSOLIDATING
→ REVIEW_READY
→ PUBLISHING
→ PUBLISHED

任一阶段失败进入 FAILED
```

候选审核状态：

```text
PENDING
CONFIRMED
MERGED
EXCLUDED
BLOCKED
```

这些状态只表示构建处理进度，不代表知识可信等级。

## 7. OKF 来源规则

- UI 可以表达为“从源文件构建 OKF”；
- 后台统一消费 Parsed Document；
- 未解析文件必须先解析或跳过；
- 每次 OKFBuild 冻结具体 `documentVersionId + parseRevisionId`；
- AI 生成的 Concept 必须绑定有效 Source Anchor；
-候选允许来自已解析但尚未发布的文档；
- 正式进入问答的 Concept，其来源文档必须可访问并建议已完成 RAG 发布。

## 8. 引用与历史版本

回答引用必须绑定本次实际使用的版本：

```text
AnswerEvidence
├── documentVersionId
├── parseRevisionId
├── publicationRevisionId
├── parentChunkId
├── matchedChildChunkIds
├── sourceAnchorSnapshot
└── excerptSnapshot
```

旧回答不能自动跳转到新文档版本。存在新版时显示提示，并分别提供“查看当时版本”和“查看最新版本”。

Source Anchor 支持四级定位精度：

```text
EXACT
PAGE
SECTION
FILE
```

PDF 优先实现页码和区域高亮；其他文件先支持章节或解析块定位。

## 9. 撤回与删除

- 撤回发布只停止参与正式检索，不删除原文件和解析结果；
- 历史 AnswerEvidence 继续指向当时的发布版本；
- 点击历史引用时重新检查权限；
- 永久删除后显示“来源已删除”，不能继续暴露敏感原文；
- 旧版本默认保留，除非执行明确的永久删除操作。
