## 6. 核实结论（先读后改）

### 6.1 `mergePreferenceJson` 浅合并语义（正确）
- patch 为 null/空白 → 返回 existing（不清除，幂等安全）✅
- existing 为 null/空白 → 返回 patch（首次设置）✅
- 两者均非空 → 解析为 `ObjectNode`，**浅合并**：patch 顶层 key 整体替换 existing 同名 key，不深层递归 ✅
- patch 为 `{}` 空对象 → 返回 existing 不变 ✅
- 任一端非 object → 回退返回 existing，不抛错 ✅
- 非法 JSON / 超深嵌套 → catch 后回退 existing，不抛错 ✅

### 6.2 禁止整体赋值（正确）
`updateCurrentUser`（L105-115）流程：
```
String merged = mergePreferenceJson(user.getPreferenceJson(), preferenceJson);
user.setPreferenceJson(normalizeOptional(merged, 8_192));
```
`setPreferenceJson` 的入参是 `merged`（合并后结果），**不是** `preferenceJson`（patch 原值）。代码审查确认无 `setPreferenceJson(preferenceJson)` 整体赋值语句。✅

### 6.3 「3 层截断」vs「64 层」口径说明（实现合理）
- Quality 措辞「嵌套 key 层级过深 3 层截断」与实现 `PREFERENCE_MAX_NESTING_DEPTH = 64` 存在数字差异。
- 经核对技术设计 §4.8.2 伪代码：只要求浅合并（顶层 key 替换），**无「3 层截断」业务要求**，也无日志要求。
- 64 层是 Jackson `StreamReadConstraints.maxNestingDepth(64)` 的**解析器防栈溢出防御**（防恶意超深嵌套导致 StackOverflowError），不是业务上的「3 层截断」。
- 业务上 preferenceJson 是浅合并，defaultModels 作为整体顶层 key 替换，不存在按层级截断的语义。64 层防御远超正常偏好 JSON 深度（defaultModels.defaults.LLM 仅 3 层），实现合理且更安全。测试 `shouldNotCrashOnOverlyDeepNesting`（5000 层）已验证超深嵌套不崩溃且回退 existing。
- 结论：实现合理，不按「3 层」修改；「3 层」为 Quality 措辞不严谨，实际意图是「防止超深嵌套」，64 层满足该意图。

### 6.4 容错与边界（正确）
- null 列、非法 JSON 字符串、嵌套超深：均回退 existing 不抛错 ✅
- `normalizeOptional(merged, 8_192)`：合并结果超 8KB 抛 `InvalidUserProfileException`，防超长存储 ✅
