# CR-011 认证令牌与接口标准化

> 功能标识：`knowledge-base-document-lifecycle`
> 变更类型：契约变更
> SDD 等级：`S2`
> 文档状态：正式
> 创建日期：2026-08-03

## 1. 变更摘要

- 变更一句话说明：将已有本地账号认证从 Cookie/CSRF 会话改为显式 `Authentication: Bearer <token>` 请求头，并统一认证相关接口的 `R<T>` 响应、异常端点和状态枚举语义。
- 本次变更结论：登录使用 `POST /auth/login` 并在 `R<SessionTokenResponse>` 返回 token；注销使用 `POST /auth/logout`；受保护请求只接受 `Authentication: Bearer <token>`；移除 Cookie token、CSRF token、CSRF 拦截器、`/auth/csrf` 端点和 Controller 本地异常处理。
- 是否建议新建 feature：否。本次只调整既有用户域认证与接口标准，未改变知识库、文档、OKF 或数据生命周期能力。

## 2. 变更原因

- 用户诉求：Controller 包位置以当前 `com.fons.cloud.ai.rag2okf.controller` 为准；所有响应体使用 Fons4Cloud `R<T>`；异常采用集中端点控制；登录后返回 token，后续使用 `Authentication: Bearer <token>`；状态判断使用枚举。
- 业务或技术背景：当前实现使用 Cookie 和 CSRF token，认证 Controller 局部返回 `ResponseEntity` 并局部处理异常，资料 Controller 直接返回 DTO；用户、工作空间和成员状态仍使用字符串字面量判断。
- 不变更的影响：前后端需要同时维护两套响应和认证约定，Cookie 自动携带引入不必要的 CSRF 处理面，字符串状态判断也会造成拼写和非法代码值的运行时风险。

## 3. 当前状态检查

- 任务规划未完成项：存在既有未完成任务；本 CR 只追加 T039，不删除或重排既有任务职责。
- 历史 CR 未完成项：CR-004、CR-005、CR-010 的本地账号、邮箱登录和职责分层结论继续有效；其 Cookie/CSRF 约束由本 CR 替换。
- 文档与代码一致性：存在差异。现有代码实际路由为 `POST /auth/login`、`POST /auth/logout`，旧技术设计为 `/auth/session`；本次已按用户确认将设计收敛到当前路由。Controller 当前包为 `com.fons.cloud.ai.rag2okf.controller`，已同步任务规划。
- 技术设计与当前实现一致性：存在差异。现有实现读取 Cookie、提供 `/auth/csrf`、使用 Controller 本地异常处理和字符串状态判断；本 CR 通过 T039 进行收敛。
- 前置条件：已满足。用户已明确确认 Bearer 请求头和登录/注销路由。

## 4. 影响范围

- 需求影响：有。AC-026、AC-027 明确登录 token 返回、Bearer 请求头和统一响应；AC-028、AC-029 由统一认证边界和枚举状态语义保障。
- 技术设计影响：有。更新认证路由、Sa-Token 读取策略、`R<T>` 响应、异常端点、CSRF 边界和状态枚举设计。
- 代码影响：有。涉及当前两个 Controller、认证/资料应用服务、认证与工作空间领域实体/策略、安全配置、CSRF 基础设施清理和测试。
- 测试影响：有。认证成功/失败、注销、资料读写、未认证、无权限、频控、统一错误响应、Bearer Header、Cookie/CSRF 残留和状态枚举均需回归。
- 接口/契约影响：有。登录/注销实际契约统一为 `POST /auth/login`、`POST /auth/logout`，所有响应体为 `R<T>`，认证请求头固定为 `Authentication: Bearer <token>`。
- 权限/安全影响：高。会话传递方式从浏览器自动 Cookie 改为客户端显式请求头；Sa-Token 禁止读取 Cookie，CSRF 防护替换为 HTTPS、受限 CORS、防 XSS 和 token 零日志/零持久化约束。
- 兼容/回滚影响：有。部署该变更后旧 Cookie 会话不再被接受，用户需要重新登录；前端必须与后端同版本发布。回滚只能回退到上一已审核构建，不能同时启用 Header 与 Cookie 双通道作为临时兼容方案。
- UI 设计确认：T002 的 UI 设计确认已通过；本 CR 不修改登录页、个人中心或注册页的信息架构、布局和交互，只调整既有 API 调用约定。

## 6. 技术设计影响

- API/RPC/消息影响：登录为 `POST /auth/login`，注销为 `POST /auth/logout`；登录响应为 `R<SessionTokenResponse>`，后续受保护请求使用 `Authentication: Bearer <token>`；不新增 RPC、消息或刷新令牌接口。
- 领域对象/业务规则影响：新增或完善用户状态、工作空间状态、成员状态和空间类型的领域枚举；保留既有 `WorkspaceRole` 枚举并由持久化映射消除字符串比较与直接 `Enum.valueOf`。
- 状态流转影响：不改变 ACTIVE/DISABLED 的业务含义，只改变 Java 侧表达和校验方式。
- 事务/一致性影响：不改变 MySQL 事务、Redis 频控 key 或 Sa-Token 会话 TTL；注销和禁用踢下线仍以当前会话/用户为边界。
- 工具化/依赖影响：复用现有 `fons4cloud-auth-satoken`、`R<T>`、`ResultCode` 和 WebMVC 全局异常处理语义；不引入依赖。

## 8. 回归与回滚

- 回归风险：认证头解析错误、token 泄露、旧 Cookie 意外继续有效、异常端点返回非 `R<T>`、错误码或 HTTP 状态漂移、枚举持久化代码不兼容、禁用踢下线失效。
- 回归验证范围：认证/注销/资料 API 契约，401/403/429/400/500，Bearer 解析，Cookie/CSRF 残留扫描，Sa-Token Redis 会话，用户/工作空间/成员状态与角色授权，token/密码/邮箱日志与响应边界。
- 回滚方案：部署前按后端与前端同版本联合验收；部署后如需回滚，恢复上一已审核应用构建并要求用户重新登录。不得以双认证通道、明文 token 日志或放宽 CORS 作为临时恢复措施。
- S2 风险门禁：必须验证 `Authentication` 头的 Bearer 前缀、Cookie 读取关闭、CSRF 残留为零、`R<T>` 全覆盖、集中异常端点、状态枚举持久化兼容、token 零日志/零持久化和受限 CORS/HTTPS 配置。

## 9. 长期知识影响

- 影响类型：技术方案、接口契约、治理规则。
